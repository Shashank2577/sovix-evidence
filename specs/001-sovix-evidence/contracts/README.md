# Contract Semantics

This directory defines planned interfaces for Sovix Evidence. [openapi.json](openapi.json),
[domain.schema.json](domain.schema.json), [events.schema.json](events.schema.json) and
[manifest.schema.json](manifest.schema.json) are generated by `scripts/build_contracts.py`;
do not hand-edit them. [operations.md](operations.md) is the generated route index. The
handwritten documents here define cross-cutting behavior that OpenAPI cannot express fully:

- [cli.md](cli.md): offline CLI, deterministic output and legacy compatibility;
- [events.md](events.md): internal event envelope, ordering, versioning and deduplication;
- [bff.md](bff.md): hosted browser authentication, session and CSRF boundary.

The generated schema is authoritative for field names and shapes. These documents are
authoritative for protocol behavior. A disagreement blocks implementation and requires the
generator or prose to be corrected before release; clients must not guess between them.

## Version and Media Types

REST routes use the `/v1` major prefix and JSON request/response bodies unless a route declares
another media type. Clients send `Accept: application/json`; errors use
`application/problem+json`. Unknown request fields are rejected where the generated schema has
`additionalProperties: false`. Timestamps are RFC 3339 instants; reporting windows are UTC
half-open `[start,end)` intervals and carry a display timezone separately. Decimal money is a
six-place string and must not pass through binary floating-point aggregation.

Backward-compatible fields or operations may be added within v1. Removing a field, narrowing
an accepted value, changing meaning or changing canonical calculation behavior requires a new
version, compatibility fixtures and at least 90 days of deprecation. Clients must treat an
unknown enum as unsupported, not as zero or success.

## Authentication and Authorization

Hosted user calls carry an audience-bound JWT from the BFF-to-API hop. Local calls carry the
random owner-readable local bearer secret and are accepted only on loopback. Collector calls
use a scoped collector bearer token. GitHub webhooks use `X-Hub-Signature-256` over the exact
raw body plus the durable delivery identity. OTLP and webhook exceptions are described below.

Every private lookup derives workspace and project access from the authenticated principal;
path IDs are selectors, never authority. The service checks current membership, project grant,
RLS context, job ownership and download authorization on every request. Inaccessible or absent
resources return the same 404. A known resource in an authorized scope whose operation is not
permitted returns 403. List responses omit inaccessible resources without revealing their
count. A cursor, ETag, job URL or export URL grants no access by itself.

Service credentials are purpose-specific: collector tokens cannot read data or administer
users, workers operate only in the leased job scope, and action workers use short-lived host
credentials. API responses never return connector, OIDC, session or object-store secrets.
Collector creation is the single deliberate exception: its new ingest token is returned once
to an authorized owner/admin, under `Cache-Control: no-store`, and cannot be retrieved later.

## Idempotency

Every state-creating REST POST requires `Idempotency-Key`, except protocol-native OTLP intake,
GitHub webhooks and BFF authentication/session endpoints, which use their own replay controls.
Keys are 1–200 visible ASCII characters, scoped to authenticated principal, workspace, HTTP
method and normalized route, and retained for 24 hours from first acceptance.

After authentication, authorization and syntactic parsing, the service atomically reserves the
key with a SHA-256 digest of the canonical request body plus behavior-changing headers and path
parameters. Query ordering and JSON member ordering do not change the digest. For the same key
and digest, a concurrent or later retry returns the original resource/job identity and the
same accepted status; once complete, it replays the stored response body. Authorization is
rechecked before replay, so revoked access returns 404 rather than the stored content. Reuse
with a different digest returns 409 `idempotency_key_reused`. After 24 hours the key may be
reused and ordinary domain uniqueness still prevents duplicate logical resources.

Validation, authentication and authorization failures are not reserved. A retry after a 5xx
may reuse the key because the reservation, when present, determines whether the original
mutation committed. Clients must use a fresh key for a deliberate new logical operation.

OTLP deduplicates by collector plus trace/span identity and sanitized digest. GitHub deduplicates
by connector plus `X-GitHub-Delivery`; an unequal verified payload for the same identity is a
conflict, not an overwrite. Policy actions additionally have domain uniqueness and provider
reconciliation rules; an `unknown` result is never blindly retried.

## Optimistic Concurrency

Mutable REST resources return a strong quoted `ETag` derived from resource ID, revision and
canonical representation. The tag is opaque to clients. Mutations marked as conditional in
OpenAPI require `If-Match` with exactly one current strong tag. Missing preconditions return
428 `precondition_required`; stale tags return 412 `revision_mismatch`; `If-Match: *` and weak
tags are rejected. A successful mutation returns the new representation and ETag. Immutable
records may return an ETag for caching but do not accept updates.

`PUT /v1/workspaces/{workspace_id}/report-definitions/{report_definition_id}/schedule` is a
special aggregate operation. Its `If-Match` is the parent ReportDefinition ETag, not a separate
schedule tag. Upserting the one allowed schedule and incrementing the parent definition revision
occur in one transaction. The response ETag is the new parent definition ETag; GET schedule
returns that same aggregate tag. This prevents a schedule update from racing with scope/window
changes that would alter what the schedule runs.

## Pagination and Filtering

List operations use opaque cursor pagination. `limit` defaults to 50 and is bounded from 1 to
100. Responses contain `items`, `next_cursor` or null, and `as_of`. The first request chooses a
stable `as_of`; subsequent cursors bind authenticated scope, route, filters, sort direction,
`as_of` and the last `(sort_value,id)` pair in a signed opaque value. Cursors expire after 24
hours, are not portable between principals, and cannot be edited. An invalid, expired or
filter-mismatched cursor returns 400 `invalid_cursor`.

Unless an operation states otherwise, private records sort newest first by their primary event
or creation timestamp and UUID as a deterministic tie-breaker; public search sorts by its
declared relevance order and stable repository ID. Records created after `as_of` appear only in
a fresh traversal. Authorization and deletion are re-evaluated on every page, so revoked rows
may disappear; `as_of` is consistency metadata, not an authorization snapshot. `start` and
`end` filters form a half-open UTC interval. Project/repository filters can narrow permitted
scope but never widen it.

## Errors and Request Metadata

REST failures use the generated `Problem` shape following RFC 9457 semantics: a stable absolute
`type`, human title, HTTP status, stable machine `code`, optional safe detail and UUID
`request_id`. Details never contain source payloads, exception messages, repository text,
secrets or another tenant's existence. Validation details identify safe field paths and reason
codes. Servers return `X-Request-ID`; a syntactically valid client-supplied UUID may be adopted,
otherwise the server generates one.

| Status | Meaning |
|---:|---|
| 400 | Malformed syntax, cursor or unsupported query combination |
| 401 | Missing, invalid or expired authentication |
| 403 | Authenticated principal cannot perform the operation on a known in-scope resource |
| 404 | Resource is absent or inaccessible |
| 409 | State, uniqueness, digest or idempotency conflict |
| 412 / 428 | Stale or missing `If-Match` |
| 413 | Compressed/decompressed body or record limit exceeded |
| 422 | Well-formed request violates a domain invariant |
| 429 | Rate/quota limit; response includes integer `Retry-After` and safe limit/reset detail |
| 503 | Required dependency unavailable before safe acceptance |

## Asynchronous Operations

Potentially long collection, import, snapshot, export, deletion, deployment, incident,
comparison and evaluation requests return 202 with a Job representation, `Location` pointing
to its scoped job route and `Retry-After: 2`. Acceptance means the command and job are durable,
not that the requested result exists. Clients poll with exponential backoff and stop at a
terminal state.

Job states are `queued`, `running`, `retrying`, `succeeded`, `partially_succeeded`, `failed`,
`cancel_requested` and `canceled`. Progress is a hint from 0 to 1 and may remain unchanged
during an indivisible step. `partially_succeeded` is terminal and names safe failed/successful
counts; it is never equivalent to complete collection. `result_url` appears only when a current
authorized result exists. A POST to the cancel route requests cooperative cancellation and may
race with a committed terminal result. Retrying a terminal user operation creates a new job
with a new idempotency key; deletion resumes its already fenced DeletionRequest as specified in
operations.md.

Policy ActionRequest is a domain aggregate, not a generic Job state machine. Its states and
transitions are exactly those in `../policy.md`: `pending_approval`, `queued`, `executing`,
`succeeded`, `refused`, `failed`, `unknown`, `cancelled`. `unknown` requires provider
reconciliation before any terminal transition and never authorizes a new mutation.

## Protocol-native Endpoints

`POST /v1/traces` is OTLP/HTTP trace intake, not a JSON REST job. It accepts the pinned
OpenTelemetry `ExportTraceServiceRequest` as `application/x-protobuf` or OTLP JSON as
`application/json`, authenticates the collector token, repeats the metadata allowlist and
returns `ExportTraceServiceResponse`. The 8 MiB limit is measured after supported decompression;
the 10,000-span and daily workspace limits apply atomically before acceptance.

Envelope/authentication/size/quota failures reject the whole request with the protocol status
and `Retry-After` when applicable. For a valid envelope, accepted sanitized spans are durable
before 200. Its native `partialSuccess` reports individual unsupported/conflicting spans using
only a rejected count and safe normalized reason; the client must not retry the accepted part
or the complete partially successful request. Logs, metrics and arbitrary trace attributes are
not accepted through alternate REST shapes.

`POST /webhooks/github` verifies the HMAC over original bytes before parsing, durably stores or
deduplicates the delivery, then returns 202. It returns 503 if durability cannot be established
so failure is visible to delivery reconciliation. Do not assume GitHub automatically retries every failed webhook; the connector must support explicit redelivery/backfill. Unknown event actions can be safely acknowledged and ignored after a
valid signature; they never become arbitrary source records.

## Contract Acceptance

- Generated artifacts reproduce byte-for-byte from the generator and validate all reference
  fixtures; no handwritten document edits a generated file.
- Cross-tenant identifier, cursor, ETag, job and download substitutions yield 404 without count
  or timing-derived disclosure.
- Same-key/same-digest POST retries return one logical result for 24 hours; a changed digest is
  409 and an authorization revocation prevents response replay.
- Schedule PUT with a stale ReportDefinition tag is 412; a valid update changes the schedule
  and parent revision atomically.
- Pagination has no duplicates within a stable traversal and rejects altered/expired cursors.
- OTLP protobuf/JSON conformance, partial success, atomic quotas and retry behavior pass pinned
  protocol fixtures without wrapping traces in the REST Job schema.

The OTLP wire baseline is [opentelemetry-proto v1.5.0](https://github.com/open-telemetry/opentelemetry-proto/tree/v1.5.0). OpenAPI describes its envelope; the upstream protobuf messages govern nested trace fields and OTLP JSON encoding. Receiver conformance requires the full pinned protocol fixtures, not only the shallow OpenAPI envelope.
